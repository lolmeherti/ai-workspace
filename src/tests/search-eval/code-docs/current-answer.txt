To create HTTP middleware in Go using the `net/http` standard library, you follow a pattern of wrapping an `http.Handler` with a function that performs logic before and/or after the core handler is executed.

### 1. The Core Signature and Pattern
Middleware is defined as a function that takes an `http.Handler` as an argument and returns a new `http.Handler`. The standard signature is:

```go
type Middleware func(http.Handler) http.Handler
```

The implementation uses **closures** to capture the `next` handler in the chain. You return an `http.HandlerFunc`, which allows you to execute logic during the "request phase" (before calling the next handler) and the "response phase" (after the next handler returns).

**Basic Implementation Template:**
```go
func exampleMiddleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        // 1. Request phase: Logic executed on the way "in"
        
        next.ServeHTTP(w, r) // Call the next handler in the chain
        
        // 2. Response phase: Logic executed on the way "out"
    })
}
```

### 2. Advanced Implementation Patterns
As applications grow, you will likely need more sophisticated patterns to manage middleware effectively:

*   **Middleware Chaining:** To avoid deeply nested function calls like `A(B(C(handler)))`, you can implement a `Chain` function. To ensure the first middleware in your slice is the **outermost** (the first to receive the request), the chain must iterate through the slice in **reverse order**.
*   **The Wrapper Pattern (Capturing Response Data):** The standard `http.ResponseWriter` does not allow you to retrieve the status code once it has been written. To log status codes, you must create a custom struct that embeds `http.ResponseWriter` and intercepts the `WriteHeader` call to store the status.
*   **The Factory Pattern (Configurable Middleware):** If your middleware needs configuration (such as a specific timeout duration), use a factory function. This is a function that accepts configuration parameters and returns the actual `Middleware` function.
*   **Context Management:** To pass data (like a User ID) from middleware to downstream handlers, use `context.WithValue`. **Best Practice:** Always use a **private, custom type** for context keys to prevent collisions with other packages.

### 3. Execution Mechanics and Best Practices
Understanding how the execution flow works is critical for debugging and security:

*   **Execution Order:** Middleware executes in the order it is wrapped. The outermost middleware is the first to receive the request and the last to process the response.
    *   *Example Flow:* `Recovery` $\rightarrow$ `Logging` $\rightarrow$ `Auth` $\rightarrow$ `Handler`
*   **Early Termination (Short-circuiting):** If a middleware determines a request should not proceed (e.g., an authentication failure), it can halt the chain by calling `http.Error` and **returning immediately** without calling `next.ServeHTTP()`.
*   **Response Modification:** If you need to add headers to a response, you must do so *before* calling `next.ServeHTTP()` or writing the response body.

### Summary of Common Middleware Types
| Type | Implementation Detail | Recommended Placement |
| :--- | :--- | :--- |
| **Panic Recovery** | Uses `defer` and `recover()` | **Outermost** (to catch all panics) |
| **Logging** | Wraps `ResponseWriter` to capture status/duration | Near the top |
| **Authentication** | Validates tokens and injects data into `r.Context()` | After logging/recovery |
| **Timeout** | Uses `context.WithTimeout` | Before heavy business logic |
