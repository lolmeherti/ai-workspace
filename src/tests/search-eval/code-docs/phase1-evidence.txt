Middleware is a fundamental concept in web application development that allows developers to process HTTP requests and responses in a modular, reusable way. In Go’s `net/http` package, middleware provides an elegant mechanism to add cross-cutting concerns such as logging, authentication, content validation, and header manipulation without cluttering your handler logic.

While many Go web frameworks offer middleware systems, Go’s standard library provides all the tools necessary to build powerful, production-ready middleware components. This article demonstrates how to develop custom middleware in Go using only the standard library, giving you complete control over your application’s request processing pipeline without external dependencies.
</chunk>
<chunk id="S1-C3" section="Building HTTP Middleware in Go: A Practical Guide Without Third-Party Dependencies &gt; What is Middleware?">
Middleware is a function that wraps an HTTP handler, allowing you to execute code before and after the handler processes a request. Think of middleware as a series of concentric layers surrounding your core business logic — each layer can inspect, modify, or even halt the request before it reaches the handler, and similarly process the response on its way back to the client.

The middleware pattern in Go follows a simple signature:

This function takes an `http.Handler` as input and returns a new `http.Handler` that wraps the original. This design enables elegant composition where multiple middleware components can be chained together, each adding its own functionality to the request processing pipeline.

**Key characteristics of middleware:**

- **Execution order**: Middleware executes in the order it’s wrapped, with the outermost middleware executing first on the way in and last on the way out.
- **Request/response access**: Each middleware has full access to both the request and response, allowing for inspection, modification, or early termination.
- **Composability**: Multiple middleware functions can be composed together, creating a flexible processing pipeline.

Now that we've covered the theory, let's look at a more practical example to give you a taste for using middleware in a real application.

In this code, we'll create two middleware functions that we want to use on all routes:

- A `serverHeader` middleware that adds the `Server: Go` header to HTTP responses.
- A `logRequest` middleware that uses the `log/slog` package to log the details of the current request.

And we'll also create a `GET /admin` route that is guarded by a `requireBasicAuthentication` middleware function, which requires the client to authenticate via HTTP basic authentication. This is another example where we will use the 'early return' pattern that we just talked about.
</chunk>
<chunk id="S2-C5" section="Using middleware on specific routes">
- We've created a middleware function called `middlewareOne`, which uses the standard pattern that we talked about above. The middleware logs a message, calls the `next` handler, and then logs another message.
- We've made two normal handler functions, `fooHandler` and `barHandler`, which both log a message and send a `200 OK` response.
- In the route `mux.Handle("GET /foo", http.HandlerFunc(fooHandler))`, we use the `http.HandlerFunc()` function to convert `fooHandler` to a `http.Handler`, and use it as normal *with no middleware*.
- In the route `mux.Handle("GET /bar", middlewareOne(http.HandlerFunc(barHandler)))`, we use the `http.HandlerFunc()` function to convert `barHandler` to a `http.Handler`, and then pass it to the `middlewareOne` function as the `next` argument. Or in simpler terms — we wrap `barHandler` with the `middlewareOne` middleware function.

If you run this application and make a request to `http://localhost:3000/foo`, you should see some log output containing only the message from `fooHandler`:

`&lt;pre class="plain"&gt;$ go run main.go&lt;samp&gt;2025/07/05 19:00:56 listening on :3000...2025/07/05 19:01:09 /foo executing fooHandler&lt;/samp&gt;&lt;/pre&gt;`In contrast, if you make a request to `http://localhost:3000/bar`, you should also see the log messages from `middlewareOne`, demonstrating that the middleware is successfully being used on that route.

`&lt;pre class="plain"&gt;&lt;samp&gt;...2025/07/05 19:02:43 /bar executing middlewareOne2025/07/05 19:02:43 /bar executing barHandler2025/07/05 19:02:43 /bar executing middlewareOne again&lt;/samp&gt;&lt;/pre&gt;`This log output also nicely illustrates the flow of control through the application code. We can see that any code in `middlewareOne` which comes *before* `next.ServeHTTP(w, r)` runs before `barHandler` is executed — and any code which comes *after* `next.ServeHTTP(w, r)` runs after `barHandler` has returned.

So the flow of control through the application for the `GET /bar` route looks like this:

`&lt;pre class="plain"&gt;http.ServeMux → middlewareOne → barHandler → middlewareOne → http.ServeMux&lt;/pre&gt;`## Using middleware on all routes

In the previous example, we used our middleware to wrap a specific handler in a specific route. But if you want your middleware to act on *all* routes, you can wrap `http.ServeMux` itself so that the flow of control looks like this:

`&lt;pre class="plain"&gt;middlewareOne → http.ServeMux → fooHandler/barHandler → http.ServeMux → middlewareOne&lt;/pre&gt;`This works because Go's `http.ServeMux` implements the `http.Handler` interface — it has the necessary [`ServeHTTP()`](https://pkg.go.dev/net/http#ServeMux.ServeHTTP) method. And as a result, we can directly pass an `http.ServeMux` into a middleware function as the `next` parameter.

Because the standard middleware function pattern accepts a `http.Handler` as a parameter, and it returns a `http.Handler`, that makes it possible to easily create arbitrarily long *chains of middleware*. Put simply, one middleware function can wrap another middleware function.

To illustrate this, let's add some more middleware functions to our example and chain them together.

When this closure is executed, any code in the closure will be run and then the `next` handler will be called.

This pattern scales well. But there are cases where the standard library genuinely falls short:

- **Path parameters**: `net/http`'s `ServeMux` gained basic wildcard support in Go 1.22 (`/users/{id}`), but complex routing (regex, optional segments) still requires a router like Chi or httprouter.
